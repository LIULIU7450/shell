## 1. 名词与背景

### 1.1 FDP 在 LMCache 中的位置

LMCache 把 KV cache 按 `chunk_size`（默认 256 token）切块，每块写入一个 key 标识的对象。FDP（Flexible Data Placement）让不同写入携带不同的 **write stream id**，由内核/设备映射为 **PLID（Placement Identifier）**，从而在 SSD 内部按"回收单元"隔离数据，降低写放大。

```
LMCache 计算的 stream_id（1..255）
      │
      ├─ ioctl FS_IOC_WRITE_STREAM { OP_SET, stream_id }（本地文件系统路径）
      └─ hf3fs_ior_set_write_stream(ior, stream_id)（3FS USRBIO 路径）
      │
      ▼
XFS（存储节点）→ 内核打印 "write with stream N" → NVMe 命令 dsmgmt=(N-1)<<16 → PLID=N-1
```

关键事实（本次环境实测）：`dsmgmt = (stream_id − 1) << 16`，即 **stream 3 → PLID 2**，stream 12 → PLID 11。

### 1.2 三处实现的分层

| 项目 | 目标文件系统 | LMCache 侧落点 | stream 下发接口 |
|---|---|---|---|
| **3FS（本项目）** | 3FS（网络 FS，FUSE + USRBIO） | `hf3fs_connector`（非 MP）/ `native_connector_l2_adapter`（MP） | `hf3fs_ior_set_write_stream()` |
| **A（ioctl 版）** | Lustre / 本地 XFS（本地 fd） | `local_disk_backend`（非 MP）/ `fs_l2_adapter`（MP） | `fcntl.ioctl(fd, FS_IOC_WRITE_STREAM)` |
| **B（FDP-main）** | 同 A | 同 A + `storage_manager` 透传 | 同 A |

★①~★⑤ 就是"分流层级"的五个关卡，下一节逐一放大。

### 2.2 分流层级精确定位

**先说结论（直接回答问题中的"pre 哪个级别"）**：

- LMCache 侧是 **pre-write，且是 batch 级**：先 `hf3fs_ior_set_write_stream()`，再 `prep` 该批的 io，形成"设置 → 快照 → 提交"的一次性批次；
- **不是 pre-flush**：USRBIO 路径没有客户端 flush 概念，数据以 chunk 写请求直接发往存储节点；
- **不是 per-io 指定**：`hf3fs_prep_io()` 没有 stream 形参，io 级无法独立选择；
- 服务端存在**第二次 pre-write**：存储 chunk engine 在每次 `pwrite` 到本地 XFS 文件**之前**调用 `FS_IOC_WRITE_STREAM`。

分级如下：

| 层级 | 粒度 | 时机 | 代码 |
|---|---|---|---|
| ★① 客户端设置 | **batch** | 一批 write 提交**前**（pre-write） | `connector.cpp:614-630` |
| ★② 快照进 io | **per-io** | `prep_io` 时把 ring 当前值复制进该 io 的 `IoArgs` | `UsrbIo.cc:733` |
| ★③ FUSE 传递 | per-io | ring 中每个 SQE 自带 `streamId` | `IoRing.cc:174-176` |
| ★④ 存储记账 | **per-chunk** | chunk update 请求携带，写入 chunk 元数据路径 | `ChunkEngine.cc:59` |
| ★⑤ 落盘应用 | **per-pwrite** | 对本地 XFS fd 每次 pwrite 前 ioctl | `cluster.rs:105-118` |

即：**LMCache 侧是"批级 pre-write"，3FS 内部把它降维成 per-io 字段，存储侧再按 chunk 记账、写盘前逐次应用。**

### 2.4 实测证据

用同一批 8 个 key（各自按 chunk key 应落不同 stream），对比两种提交方式（3 存储节点内核计数合计）：

| 提交方式 | 命中的业务 stream | 内核计数增量 |
|---|---|---|
| 8 个 key **一次 batch** | **1 个**（stream 3） | `{3: 768}` |
| 8 个 key **分 8 次 batch** | 8 个（stream 3–10） | `{3:96, 4:96, …, 10:96}` |

（`stream 2` 是 3FS compaction，`15/16` 是 XFS 元数据保留流，均为背景噪声。）

**结论**：分流粒度 = **batch**，不是 key、不是 io。

### 2.5 边界条件与已知问题

| 情况 | 行为 |
|---|---|
| `use_fdp=False` 或 `fdp_stream_number<=0` | `stream_id=0`，整批默认放置，不调用 set |
| `set_write_stream` 失败（stream>255） | 整批降级默认放置，打印 `[LMCache FDP] set_write_stream(...) failed` |
| `num_workers>1` | 每个 worker 有独立 `write_ior`；不同批并发用不同 stream 是安全的（同 worker 内串行） |
| 一个 chunk 的 6 个副本 | 都带同一 stream（stream 随客户端请求下发到各副本的存储节点） |
| **`stream_id == 0` 时未重置** | `if (stream_id > 0)` 才 set，ior 上的旧值会"粘住"；当前配置不会触发，但属隐患（应无条件 set，0 合法） |

## 3. 与 A / B 项目的 MP 模式对比

### 3.1 三者的 MP 链路

**A / B（Lustre / 本地盘）**

```
FsL2Adapter.submit_store_task(keys, objs)
  ├─ [A] request_id = keys[0].request_id（整型）
  │      stream = ruh_map[trace_name][rid % len] + 1
  │               or rid % N + 1
  └─ [B] request_id = keys[0].request_id
         stream = ruh_map[...] or rid % N + 1
  └─ _execute_store(..., stream_id)
       └─ _write_with_odirect(path, buf, stream_id)
            fd = os.open(path, O_CREAT|O_WRONLY|O_DIRECT)
            fcntl.ioctl(fd, FS_IOC_WRITE_STREAM, {OP_SET, stream_id})   ← per-file
            os.write(fd, buf)
            os.close(fd)
```

**3FS（本项目）**

```
NativeConnectorL2Adapter.submit_store_task(keys, objs)
  hint = keys[0] 的序列化串（chunk key）
  stream = start + md5(hint)%N
  └─ LMCacheHf3fsClient.submit_batch_set(keys, memviews, stream)
       └─ hf3fs_ior_set_write_stream(ior, stream)      ← per-batch（ring）
          for key: open→prep(io)→submit→wait→close
```

### 3.2 差异点逐一对比

| # | 维度 | A / B（MP） | 3FS（MP） | 影响 |
|---|---|---|---|---|
| 1 | **I/O 通道** | 本地 fd（`os.open` + `O_DIRECT` + `os.write`） | 3FS USRBIO（共享内存 ring + `prep/submit/wait`） | 决定 stream 挂在哪里 |
| 2 | **stream 承载对象** | **文件描述符**（内核 XFS 的 fd 属性） | **IoRing**（用户态 ring + 共享内存 `IoArgs.streamId`） | 根本差异 |
| 3 | **可设置粒度** | **per-file**（每写一个文件可独立设置） | **per-batch**（一次 set 覆盖该批所有 io） | 3FS 无法做到 per-key |
| 4 | **API 形态** | `ioctl(fd, FS_IOC_WRITE_STREAM, …)` | `hf3fs_ior_set_write_stream(ior, sid)` | ioctl 号也不同（本地 XFS vs USRBIO） |
| 5 | **设置时机** | `open()` 之后、`write()` 之前 | `prep_io()` 之前（prep 时快照）；实际生效于 prep |

| 8 | **批内一致性** | 天然 per-key（每个文件独立） | 批内强制一致（批首 key 代表整批） | 3FS 有"同化"现象 |
| 9 | **ruh_map（workload→RU 列表）** | 支持 | 不支持 | 3FS 无 workload 概念映射 |

| 11 | **设备能力探测** | `_get_fdp_max_streams()`（GET_MAX ioctl）自动夹紧 | 无探测，靠配置校验 `start+N-1 ≤ 255` | 3FS 建议人工按 `GET_MAX=14` 配 |
| 12 | **多线程模型** | 每个 I/O 一个 fd，天然隔离 | 每 worker 一个 ior + `WorkerHf3fsConn`，同 worker 内串行 | 并发批不能共享 ior |
| 13 | **stream 生命周期** | 打开文件期间有效，close 即结束 | **粘在 ior 上**，直到下次 set | 有"零值不重置"隐患 |
| 14 | **下游传播** | 无（本地盘直接落盘） | FUSE → StorageClient → 存储 chunk engine → 本地 XFS pwrite 前再 ioctl | 3FS 全链路多两层 |
| 15 | **能否 per-io 指定** | 不需要（per-file 已足够） | **不能**（`hf3fs_prep_io` 无 stream 形参） | 决定性约束 |

### 3.3 关键差异归纳

1. **承载对象不同**：A/B 的 stream 是"**文件描述符的属性**"，3FS 的 stream 是"**I/O 环形队列的属性**"。
2. **粒度不同**：A/B 天然 **per-file**；3FS 只能 **per-batch**。
3. **信息不同**：A/B 的 MP 用 **request_id（请求级）**，3FS 用 **chunk key（内容级）**。
4. **路径更长**：3FS 的 stream 要跨 FUSE → 存储节点 → 本地 XFS 三段，A/B 只在本机一步。

## 4. 设计动机与必要性

### 4.1 为什么不能沿用 A/B 的 `fd ioctl` 方案

**原因一：3FS 的客户端 fd 是 FUSE 文件，本地 XFS 的 ioctl 对它无效。**

A/B 的 `fcntl.ioctl(fd, FS_IOC_WRITE_STREAM, …)` 作用于**本地 XFS inode**，由内核 VFS 分发给 XFS。而 3FS 客户端的 fd 指向 `hf3fs.stage` 挂载点下的文件，该 ioctl 会被分发给 hf3fs 的 FUSE 驱动——3FS 为此单独定义了 `HF3FS_IOC_WRITE_STREAM`（`_IOWR('h', 16, …)`，值 `0xC0106810`），与本地 XFS 的 `FS_IOC_WRITE_STREAM`（`_IOWR('f', 43, …)`，值 `0xC010662B`）**不是同一个接口**；即便使用前者，也只作用于 FUSE 的同步写路径，不会影响 USRBIO 提交的 io 请求。

**原因二：USRBIO 绕过 VFS，ioctl 根本到不了数据路径。**

3FS 的高性能路径是 USRBIO：客户端把 io 参数写进 `/3fs/stage/3fs-virt/iovs/...` 共享内存 ring，FUSE 守护进程直接消费 ring，**不经过 `write(2)` 系统调用**。即使对 fd 调了 ioctl，也不会影响 ring 里的 io 请求。因此 3FS 必须在**提交到 ring** 的环节设置 stream，即 `hf3fs_ior_set_write_stream`。

**原因三：USRBIO 的 stream 是 ring 级，不是 io 级。**

这是最硬的约束，见 §5.1。LMCache 想在 per-key 粒度设置 stream，但 USRBIO 根本不提供"这个 io 用 stream A、那个 io 用 stream B"的接口。

### 4.2 为什么只能在"提交前按批设置"

因为 stream 在 `prep_io` 时被快照进每个 io 的 `IoArgs`（`UsrbIo.cc:733`）。一旦 prep 完成，该 io 的 stream 就固定了；要改只能对**尚未 prep 的 io** 生效。

LMCache 的写入流程是"一次 `submit_batch_set` 里循环 open→prep→submit→wait"，如果想让批内不同 key 用不同 stream，就必须：

- 在批内**穿插** `set_write_stream`（每 prep 一个 key 前 set 一次），或
- 每个 key 单独一个 batch（即每 key 一次 submit）

前者需要改 C++ connector 的 `do_batch_set`（把 set 从批级下沉到 key 级），后者需要改 Python 侧提交粒度（放弃批量）。两者都不是"配置层能解决"的问题。

### 4.3 为什么 hint 只能是 chunk key

| 条件 | 现状 |
|---|---|
| `ObjectKey` 有无 `request_id` | **无**（只有 `chunk_hash/model_name/kv_rank/cache_salt`，`api.py:23-58`） |
| `L2AdapterInterface.submit_store_task` 入参 | `(keys, objects)`，**无 id 参数**（`base.py:201-205`） |
| MP 的 `IPCCacheEngineKey.request_id` | 存在，但 `field(compare=False)`，注释明确"仅用于 session 跟踪，不属于缓存身份"，且在 `ipc_key_to_object_keys()`（`api.py:184`）处被丢弃 |
| `select_fdp_hint_key()` | 有实现，但**生产代码零调用**（仅单测） |
| `fdp_hint_source` 配置 | 可解析 `request_id`/`user_id`，但**只用于打印日志**（`native_connector_l2_adapter.py:130-138`） |

因此在现有接口下，adapter 唯一能拿到的稳定标识就是 **chunk key**。这一点与 A/B 形成鲜明对比：A 的 `ObjectKey` 专门加了 `request_id` 字段（`api.py:66`，注释写明"metadata，不入 equality/hash"），B 又在非 MP 路径补了 `storage_manager.batched_put(request_id, user_id)` 的透传。

### 4.4 为什么 chunk 级分流反而合理

即便能改，chunk 级分流在 3FS 上也更合适：

| 维度 | request 级（A/B 思路） | chunk 级（3FS 现状） |
|---|---|---|
| 同一 chunk 跨请求 | 落不同 PLID → 同内容重复写不同 RU | 恒同 PLID → 无重复分散 |
| 跨实例/重启 | 依赖 request_id 生成规则一致 | 与内容绑定，天然一致 |
| 前缀缓存命中场景 | 命中即重复写 | 命中后可稳定复用同一 PLID 区域 |
| 实现成本 | 需改 ObjectKey + 接口 + 批边界 | 零改动 |

3FS 的 KV 复用率极高（前缀缓存），同一 chunk 会在大量请求中重复出现；按请求分流会让同一份数据反复落到不同回收单元，**对 WAF 是负优化**。

## 5. 源码级论证：hf3fs 为什么"天生"不支持 per-io / per-key

### 5.1 约束一：`hf3fs_prep_io()` 没有 stream 形参

```168:177:/home/smrc/lzh/3fs-main/src/lib/api/hf3fs_usrbio.h

                  const struct hf3fs_iov *iov,
                  bool read,
                  void *ptr,
                  int fd,
                  size_t off,
                  uint64_t len,
                  const void *userdata);
```

形参共 8 个，无 stream。整个 USRBIO C API 里与 stream 相关的只有：

- `hf3fs_iorcreate5(..., stream_id)`（创建时指定，ring 级）
- `hf3fs_ior_set_write_stream(ior, stream_id)`（运行时设置，ring 级）

→ **没有任何接口能在 io 粒度指定 stream**。

### 5.2 约束二：stream 存在 `struct hf3fs_ior` / `IoRing` 上

```32:46:/home/smrc/lzh/3fs-main/src/lib/api/hf3fs_usrbio.h

  struct hf3fs_iov iov;
  hf3fs_ior_handle iorh;
  ...
```

```173:178:/home/smrc/lzh/3fs-main/src/fuse/IoRing.h

  uint64_t streamId() const { return streamId_; }
  void setStreamId(uint64_t sid) { streamId_ = sid; }
  ...
  uint64_t streamId_{0};
```

`ior->stream_id` 与 `IoRing::streamId_` 都是**单值**，天然表示"当前 ring 的写流"。一个 ring 同时只能有一个 stream 值。

### 5.3 约束三：stream 参与 ring 的共享内存命名，说明它是"ring 身份"

```156:/home/smrc/lzh/3fs-main/src/lib/api/UsrbIo.cc

```

`hf3fs_iorcreate5` 把 stream 编进 iov/ring 的符号链接名（`.s3` 之类）。这进一步说明设计上 stream 是 **ring 的属性**，而不是请求的属性——同一个 ring 的多次提交共享它。

### 5.4 约束四：stream 在 `prep` 时快照，`submit` 不再读取

```727:733:/home/smrc/lzh/3fs-main/src/lib/api/UsrbIo.cc

  ...
  args.streamId = ior->stream_id;  // propagate FDP stream ID per-IO via shared memory
```

```750:759:/home/smrc/lzh/3fs-main/src/lib/api/UsrbIo.cc

  ...
  auto &iorh = *(Hf3fsIorHandle *)ior->iorh;
  sem_post(iorh.submitSem);
  return 0;
}
```

`submit` 只是 `sem_post` 唤醒 FUSE 线程，不再读 stream。因此 **stream 的"生效点"是 prep**。LMCache 的 `do_batch_set` 在批开始时 set 一次，正好覆盖"该批全部 prep"。

### 5.5 约束五：存储侧是 chunk 级记账，必须逐次应用

```56:62:/home/smrc/lzh/3fs-main/src/storage/store/ChunkEngine.cc

```

```85:118:/home/smrc/lzh/3fs-main/src/storage/chunk_engine/src/file/cluster.rs

            // The stream is per-fd in the kernel; we re-apply it on every iteration
            if stream_id != 0 {
                let rc = crate::cxx::set_write_stream(raw_fd, stream_id);
```

存储节点对同一个 chunk 文件可能分多次 pwrite（分片/重试），每次都要重新 ioctl，因为**内核侧 stream 是 fd 属性、且会被其他写覆盖**。这恰好反证：连存储节点内部都无法"一次设置、永久生效"。

### 5.6 约束六：`fs_write_stream` 是文件系统级接口，只有 16 字节

```375:390:/home/smrc/lzh/3fs-main/src/storage/chunk_engine/src/cxx.rs

/// struct fs_write_stream { __u32 op_flags; __u32 stream_id; __u32 max_streams; __u32 rsvd; } = 16 bytes.
const FS_IOC_WRITE_STREAM: libc::c_ulong = 0xC010662B;
```

结构体只有 `op_flags / stream_id / max_streams / rsvd` 四个字段，**没有任何 per-io 定位信息**（如 offset 范围、请求 id）。内核 API 本身也只支持"对某个 fd 设置当前流"。

### 5.7 小结：约束链

```
内核 FS_IOC_WRITE_STREAM 只能作用于 fd（无 per-io 语义）
        ↓（3FS 是网络 FS，客户端 fd 走 FUSE，且 USRBIO 绕过 VFS）
3FS 在 USRBIO 层提供等价能力 → 但只能定义在 IoRing 上
        ↓（IoRing 是 per-worker 的、单值 stream）
一次 set 覆盖整批 prep 的 io
        ↓（LMCache 一批由 StoreController 聚合、跨请求）
批内无法区分 request / user
        ↓（ObjectKey 无 request_id、adapter 接口无 id 入参）
唯一稳定可用的 hint = chunk key
        ↓
stream = start + md5(chunk_key) % N
```

这条链上的每一环都有源码支撑，说明 **"chunk key + 批级设置"不是设计偷懒，而是 hf3fs 数据通路的必然结果**。

## 6. 结论与建议

### 6.1 结论

1. **分流层级**：3FS 版是"**客户端批级 pre-write（ioring 状态）+ prep 时 per-io 快照 + 存储侧 per-chunk 记账 + pwrite 前逐次 ioctl**"，最终落到内核 FDP 的点在存储节点的 XFS pwrite（`cluster.rs:105-118`）。
2. **分流粒度**：**batch**。一批内所有 chunk 共用批首 key 算出的 stream（实测：一批 8 key → 仅 1 个 stream；拆成 8 批 → 8 个 stream）。
3. **与 A/B 的根本差异**：A/B 的 stream 挂在 **fd** 上（per-file），3FS 挂在 **IoRing** 上（per-batch）；A/B 的 MP 用 **request_id**，3FS 用 **chunk key**。
4. **不能沿用原方案的原因**：USRBIO 无 per-io stream 形参（`hf3fs_usrbio.h:168`）、stream 是 ring 单值属性（`UsrbIo.cc:577`）、prep 时快照（`UsrbIo.cc:733`）、存储侧仅支持 fd 级 ioctl（`cxx.rs:377`）。四者共同决定 LMCache 只能在批边界设置 stream。
5. **chunk key 的合理性**：在 3FS 高复用场景下，chunk 级映射比 request 级更稳定，避免同内容重复落到不同回收单元。

### 6.2 建议

| 优先级 | 建议 |
|---|---|
| P0 | 修复 `stream_id == 0` 不重置的问题：`connector.cpp` 改为无条件调用 `set_write_stream`（0 合法，表示默认放置） |
| P0 | 配置层收敛 `fdp_hint_source`：只保留 `chunk_key`（默认）/ `user_id`；`request_id` 显式拒绝并提示，避免"看起来能切、实际无效" |
| P1 | 若要支持 user 级分流：用 `ObjectKey.cache_salt` 作 hint（1 行改动），并在 `StoreController._submit_store_for_single_shape()` 按 salt 分组提交，保证"批 ⊆ 用户" |
| P1 | 在 `docs/openspec/specs/hf3fs-fdp-write-stream/spec.md` 中把 stream 计算改为"chunk key + 批级"，并补"批内同化"说明 |
| P2 | 补测试：`test_hf3fs_l2_adapter.py` 目前 0 条 FDP 用例；至少覆盖"一批多 key → 单 stream""拆批 → 多 stream""stream=0 不粘滞" |
| P2 | 若要真正 per-key 分流：需改 C++ `do_batch_set`（set 下沉到 key 级）或按 key 拆批；前者改动小但需评估 `set` 的额外开销（每次 set 是一次用户态赋值 + 可选日志） |
