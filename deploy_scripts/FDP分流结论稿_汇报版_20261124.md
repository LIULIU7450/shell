## 第一章 总体结论

本项目的 FDP 分流在 **MP 模式下按批次（batch）实施**：写入前设置 I/O 环形队列的写流标识，该批次内全部数据共享同一 stream id，最终由存储节点在持久化阶段落至本地文件系统与设备放置单元。

该设计并非实现层面的取舍，而是 **hf3fs 后端数据通路的结构性约束所致**；沿用参考项目基于文件描述符的逐文件设置方案，在 3FS 上不具备可行性。

---

## 第二章 关键结论

### 2.1 stream id 的计算方式

MP 模式下，stream id 由该批次首个对象的内容标识（chunk key）经哈希取模得出，计算公式为：

```
hint_key  = <model_name>@<kv_rank>@<chunk_hash>[@<cache_salt>]
stream_id = start_fdp_stream_id
            + ( int( MD5(hint_key)[:8], 16 ) mod fdp_stream_number )
```

计算过程可归纳为四步：

1. 取该批次**第一个**对象的序列化标识作为 `hint_key`；
2. 对其计算 MD5，取十六进制摘要前 8 位并转换为 32 位整数；
3. 以 stream 个数（`fdp_stream_number`）为模取余，得到 `[0, N-1]` 区间内的偏移量；
4. 叠加起始编号（`start_fdp_stream_id`），得到最终 stream id，取值范围为 `[start, start+N-1]`。

算例（`N=8`、`start=3`）：`hint_key` 为 `m@00000000@00000002` 时，MD5 前 8 位为 `302f6f4f`，其整数值为 808415055，对 8 取余得 7，加 3 后为 **stream 10**。

当未启用 FDP，或 stream 个数配置为 0 及以下时，stream id 取 0，表示不携带放置指令，由设备默认处理。

### 2.2 分流层级

分流发生在**写入之前（pre-write）**，具体为两个阶段：

1. **客户端**：在一批写入提交前设置环形队列的写流标识，属**批级 pre-write**；该设置在每个 I/O 准备阶段被固化为请求参数，提交后不再变更。
2. **存储节点**：按 chunk 记录所属 stream，并在每次写入本地文件系统**之前**重新应用，属**服务端 pre-write**。

分流不发生在文件刷写（flush）阶段，亦不支持逐个 I/O 单独指定。

### 2.3 分流粒度

粒度为**批次**，而非单个对象、单个 I/O 或单个请求。同一批次内的全部 KV chunk 共用由该批首个对象确定的 stream id。

经实测核验：八个本应分属八个 stream 的对象，若一次提交，仅落于一个 stream；拆分为八次提交，则分别落于八个 stream。

### 2.4 与参考方案差异的实质

与两个参考项目（基于本地/Lustre 文件系统）相比，差异集中于三点：

1. **承载对象不同**：参考方案的 stream 附属于**文件描述符**，本项目附属于 **I/O 环形队列**。
2. **可设置粒度不同**：参考方案天然支持**逐文件**设置，本项目仅支持**逐批次**设置。
3. **映射依据不同**：参考方案采用**请求标识**，本项目采用**对象内容标识（chunk key）**。

### 2.5 方案不可沿用的判定

参考方案依赖"打开文件后、写入之前对描述符设置写流"的接口语义。该语义在 3FS 上不成立，原因有三：

1. 3FS 为网络文件系统，客户端描述符对应的并非本地文件系统接口；
2. 其高性能通路绕过常规写入系统调用，描述符级设置无法作用于实际 I/O；
3. 后端接口未提供逐 I/O 指定写流的参数，写流标识只能作为队列级属性存在。

据此判定：**在现有 hf3fs 接口下，无法实现逐对象或逐请求的写流设置**。

### 2.6 映射策略的适配性

以对象内容标识作为映射依据，在当前场景下具备合理性：同一内容在不同请求、不同实例与重启前后始终保持一致的 stream 归属，可避免同一数据重复落入不同回收单元，有利于降低写放大。相较之下，请求级映射会导致同一内容在不同请求中发生归属漂移。

## 第三章 影响与风险

1. **分布特征需正确解读**：运行期出现"单一 stream 计数显著增长、其余接近为零"属预期现象，不代表分流失效。
2. **配置项存在误导风险**：现有配置支持"请求标识/用户标识"选项，但该选项未参与实际计算，易使使用方误判分流策略已切换。
3. **状态残留隐患**：写流标识在未显式重置的情形下会保留于队列，若后续引入动态开关，可能导致本应默认放置的写入仍携带先前标识。
4. **测试覆盖不足**：现有 FDP 相关测试未覆盖批次粒度行为，上述特征缺乏回归保护。

---

## 第四章 建议事项

| 优先级 | 建议事项 |
|---|---|
| P0 | 修正写流标识未重置的行为，确保标识为默认值时亦显式下发 |
| P0 | 收敛配置项取值范围：保留"内容标识"为默认，明确"用户标识"的适用方式，对不生效取值显式拒绝并提示 |
| P1 | 若需支持用户级分流，以对象中的用户隔离字段为依据，并在提交环节按该字段分组，保证"批次从属于单一用户" |
| P1 | 同步更新规格文档，将映射方式表述为"内容标识 + 批次粒度"，并补充批内共享的说明 |
| P2 | 增补测试用例，覆盖"单批多对象""拆批""默认标识不残留"三类场景 |
| P2 | 如需逐对象分流，应评估下沉设置位置或调整提交粒度，并同步评估性能影响 |

---

## 第五章 结论适用范围

1. 本结论适用于 **MP 模式、经 3FS 用户态 I/O 环形队列**的写入路径。
2. **非 MP 路径不适用**：该路径为逐对象同步写入，具备逐对象设置写流的条件，其行为与 MP 路径不同。
3. 本结论不涉及存储节点的压缩/整理（compaction）专用写流，该写流由存储侧独立配置。
4. 本结论以当前部署版本的 hf3fs 接口为准；若后端接口新增逐 I/O 写流能力，需重新评估。

## Chapter 1 Overall Conclusion

In MP mode, FDP stream assignment in this project is performed **per batch**. The write stream identifier is set on the I/O ring before the batch is submitted; all data within that batch shares a single stream id, which is ultimately applied to the local file system and to the device placement units by the storage node during persistence.

This behaviour is not an implementation preference but a **structural constraint of the hf3fs data path**. The per-file scheme of the reference projects, which sets the stream on a file descriptor, is not feasible on 3FS.

---

## Chapter 2 Key Conclusions

### 2.1 Computation of the Stream Identifier

In MP mode the stream id is derived, by hash and modulus, from the content identifier (chunk key) of the first object in the batch:

```
hint_key  = <model_name>@<kv_rank>@<chunk_hash>[@<cache_salt>]
stream_id = start_fdp_stream_id
            + ( int( MD5(hint_key)[:8], 16 ) mod fdp_stream_number )
```

The computation comprises four steps:

1. the serialised identifier of the **first** object in the batch is taken as `hint_key`;
2. its MD5 digest is computed and the first eight hexadecimal characters are converted to a 32-bit integer;
3. the remainder modulo the stream count (`fdp_stream_number`) yields an offset within `[0, N-1]`;
4. the offset is added to the start identifier (`start_fdp_stream_id`), producing a stream id within `[start, start+N-1]`.

Example (`N=8`, `start=3`): for `hint_key` equal to `m@00000000@00000002`, the first eight MD5 characters are `302f6f4f`, whose integer value is 808415055; the remainder modulo 8 is 7, and adding 3 yields **stream 10**.

When FDP is disabled, or the stream count is configured as zero or less, the stream id is 0, indicating that no placement directive is issued and placement is left to the device default.

### 2.2 Level of Assignment

Assignment occurs **before the write (pre-write)**, in two stages:

1. **Client side**: the ring-level write stream identifier is set before a batch is submitted, constituting **batch-level pre-write**; the value is frozen into each request during I/O preparation and is not altered at submission.
2. **Storage side**: the stream is recorded per chunk and re-applied **before each write** to the local file system, constituting **server-side pre-write**.

Assignment does not occur at the flush stage, and per-I/O specification is not supported.

### 2.3 Granularity

The granularity is the **batch**, not the individual object, I/O or request. All KV chunks in a batch share the stream id derived from the first object of that batch.

Verification confirmed that eight objects which should map to eight distinct streams occupy only one stream when submitted as a single batch, and eight streams when submitted as eight batches.

### 2.4 Substance of the Divergence from Reference Schemes

Three differences are material when compared with the two reference projects based on local/Lustre file systems:

1. **Carrier**: in the reference schemes the stream belongs to a **file descriptor**; here it belongs to the **I/O ring**.
2. **Granularity**: the reference schemes support **per-file** assignment; this project supports **per-batch** assignment only.
3. **Mapping basis**: the reference schemes use a **request identifier**; this project uses the **object content identifier (chunk key)**.

### 2.5 Determination that the Reference Scheme Cannot Be Adopted

The reference scheme relies on the semantics of setting a write stream on a descriptor between open and write. These semantics do not hold on 3FS for three reasons:

1. 3FS is a network file system, and a client descriptor does not correspond to a local file system interface;
2. its high-performance path bypasses the conventional write system call, so descriptor-level settings cannot reach the actual I/O;
3. the backend interface exposes no per-I/O stream parameter, so the stream identifier can only exist as a queue-level attribute.

It is therefore determined that **per-object or per-request stream assignment is not achievable under the current hf3fs interface**.

### 2.6 Suitability of the Mapping Strategy

Using the object content identifier as the mapping basis is appropriate for the present workload: the same content retains an identical stream across requests, instances and restarts, which prevents the same data from being written repeatedly into different reclaim units and thereby supports write-amplification reduction. A request-level mapping, by contrast, causes the same content to drift between streams across requests.

## Chapter 3 Impact and Risks

1. **Distribution characteristics require correct interpretation**: a markedly growing count on a single stream with near-zero counts elsewhere is expected behaviour, not an indication of failure.
2. **Configuration options are potentially misleading**: existing options expose request-identifier and user-identifier modes that do not participate in the actual computation, which may lead users to believe the strategy has been switched.
3. **Residual state**: the stream identifier persists on the ring unless explicitly reset; should a dynamic switch be introduced, writes intended for default placement may still carry the previous identifier.
4. **Insufficient test coverage**: existing FDP tests do not cover batch-granularity behaviour, leaving the above characteristics without regression protection.

---

## Chapter 4 Recommendations

| Priority | Recommendation |
|---|---|
| P0 | Correct the behaviour whereby the stream identifier is not reset, ensuring the value is explicitly issued even when it is the default |
| P0 | Constrain configuration values: retain the content identifier as the default, define the applicable use of the user identifier, and explicitly reject non-effective values with a warning |
| P1 | Should user-level assignment be required, base it on the user isolation field of the object and group submissions by that field so that a batch belongs to a single user |
| P1 | Update the specification to describe the mapping as "content identifier with batch granularity" and to document intra-batch sharing |
| P2 | Add test cases covering single-batch multi-object, batch splitting, and non-residual default identifier |
| P2 | If per-object assignment is required, evaluate relocating the setting point or adjusting submission granularity, together with the performance impact |

---

## Chapter 5 Scope of Applicability

1. This conclusion applies to the **MP mode write path through the 3FS user-space I/O ring**.
2. It does **not apply to the non-MP path**, which performs per-object synchronous writes and is therefore able to set the stream per object; its behaviour differs from that of MP mode.
3. This conclusion does not address the dedicated stream used by storage-side compaction, which is configured independently.
4. This conclusion reflects the hf3fs interface of the currently deployed version; should the backend expose per-I/O stream capability in future, the assessment must be revisited.
